## 1. 原型业务复杂度分析

通过全量路由与核心页面走查，原型功能结构如下：

| 模块        | 页面                                                                        | 复杂度特征                                                                        |
| ----------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 仪表盘      | 总览                                                                        | KPI 卡片、趋势/占比图表、日期范围切换、四步初始化引导向导                         |
| 身份管理    | 用户 / 用户组 / 角色 / API Key                                              | 部门树 + 多条件筛选表格、批量启停删、导入用户、角色复制、Key 脱敏展示             |
| 模型接入    | 供应商 / 物理模型 / 逻辑模型                                                | 供应商模板表单、"获取模型"联动、逻辑模型-物理模型映射、按部门/用户组/用户三维授权 |
| 成本与预算  | 消费账单 / 预算管理 / 审批                                                  | 总部-部门-用户三级预算、共享/独占模式、使用率进度、账单多维度表格                 |
| AI 安全治理 | 访问控制 / 敏感数据规则 / 安全检测                                          | 策略优先级拖拽排序、32 类敏感数据规则分类树、检测能力配置、脱敏策略               |
| 审计中心    | 访问审计 / 安全事件 / 审计报表                                              | 16+ 列宽表格、会话详情、事件批量审核、白名单、多维度报表（图表+导出）             |
| 系统管理    | 通用配置 / 检测能力 / 插件 / 集群 / License / 升级 / 备份恢复 / 健康 / 日志 | 配置表单组、集群节点状态、版本升级向导、日志检索                                  |
| 个人中心    | 使用概览 / API Keys / 访问记录 / 安全记录 / 预算                            | 个人用量图表、Key 自助管理                                                        |

**复杂度结论**：典型的中高复杂度企业级中后台。核心组件诉求为：

1. **强表格**：排序、筛选、批量操作、展开行、固定列、虚拟滚动（审计记录量级）；
2. **树**：部门树、规则分类树（Tree + 表格联动）；
3. **复杂表单**：多步骤向导（初始化引导、供应商接入、系统升级）、联动校验、密码策略等动态规则；
4. **图表**：仪表盘、成本趋势、审计报表、使用分析（柱/线/饼/排行）；
5. **通用能力**：日期范围、导入导出、脱敏展示、标签状态、拖拽排序、抽屉/对话框详情。

**扩展性要求**：P1 功能（智能路由、流程管理、使用分析、联动管理等约 10 个页面）本期不开发，但菜单与路由已占位，架构必须支持**按业务域插拔**，P1 上线时不改动既有代码。

## 2. 选型结论（一览）

| 分层     | 选型                                                    | 说明                             |
| -------- | ------------------------------------------------------- | -------------------------------- |
| 框架     | **Vue 3（Composition API + `<script setup>`）**         | 原型同构                         |
| 语言     | **TypeScript**                                          | 中后台长周期维护必备             |
| 组件库   | **TDesign Vue Next**（已选定）                          | 与原型 1:1 同构                  |
| 构建     | **Vite**                                                | 现代浏览器目标，无需 legacy 包袱 |
| 状态管理 | **Pinia**                                               | 官方推荐，按业务域分 store       |
| 路由     | **Vue Router**                                          | 动态权限路由 + 菜单配置化        |
| 图表     | **ECharts**（按需引入）                                 | 仪表盘/成本/审计报表             |
| HTTP     | **Axios** 统一封装 + **Mock（vite-plugin-mock / MSW）** | REST 并行开发                    |
| 工程化   | ESLint + Prettier + Stylelint + husky + lint-staged     | 提交卡口                         |

## 3. 框架选型：Vue 3 vs React

### Vue 3

**优点**

- **专精**：主力技术栈，开发效率、踩坑成本、代码评审质量均有保障；
- **与原型同构**：原型即 Vue 3.5 实现，交互逻辑、路由结构（55 个路由已验证）可直接对照迁移，还原成本最低；
- **中后台适配性好**：模板 + 响应式系统天然适配"表单 + 表格"密集型页面，双向绑定在复杂筛选表单（访问审计 16+ 列筛选）场景下显著少于 React 的受控样板代码；
- **生态匹配**：Vue Router（动态权限路由）、Pinia（模块化状态）官方全家桶，长期维护稳定。

**缺点**

- 超大型项目的类型体操与 JSX 灵活性弱于 React（本项目用不到）；
- 社区总量小于 React，但中后台场景生态已完全成熟。

### React

**优点**

- 生态最大，复杂交互（如未来的路由拓扑可视化）组件选择更多；
- TypeScript 结合最紧密。

**缺点**

- 仅"略通"，在 45+ 页面的体量下，Hooks 心智负担（依赖数组、重渲染优化）会直接拖慢交付；
- 组件库 Antd 虽强，但选择 React 意味着放弃原型既有实现，等于推翻重来；
- 中后台"表单+表格"场景样板代码量大于 Vue。

### 结论

**选 Vue 3**。专精度、原型同构、中后台开发效率三个维度均压倒性占优；React 的生态优势在本项目场景（标准中后台，无极端交互）不构成实际收益。

## 4. 组件库对比：TDesign（选定）vs Element Plus vs Ant Design Vue

> 说明：候选中的 Antd 主战场在 React；Vue 技术栈下对应实现为 Ant Design Vue。ElementU 的 Vue 3 版本为 Element Plus。

### TDesign Vue Next（选定）

**优点**

- **与原型 1:1 同构**：原型即 TDesign 实现，设计规范、组件交互、间距体系零偏差还原，视觉走查成本几乎为零；
- **企业级组件完备**：增强 Table（排序/筛选/固定列/展开行/拖拽）、Tree、Form 联动校验、DateRangePicker、Transfer、Steps 向导，覆盖原型全部组件诉求（见第 1 节清单）；
- **Vue 3 原生 + 全量 TypeScript**：Composition API 风格一致，类型声明质量高；
- **腾讯持续维护**，版本节奏稳定；内置暗色主题与国际化能力，为未来扩展留口；
- 设计令牌（Design Token）体系完善，便于统一定制品牌色（安全网关类产品常见诉求）。

**缺点**

- 社区规模与第三方周边（封装组件、教程）小于 Element / Antd 生态，遇到冷门问题时检索成本略高；
- Pro 级封装（如高级筛选表格、描述列表）弱于 Ant Design Pro，需要项目内自封装一层"筛选区 + 表格"业务组件（本期正好借此沉淀）。

### Element Plus

**优点**

- Vue 生态中社区最大、资料最多，招聘熟悉度高；
- 组件稳定性好，Bug 存量透明。

**缺点**

- 设计语言偏老，与原型视觉体系差异大，还原需大量覆盖样式，**等于为每个页面额外支付一次 UI 对齐成本**；
- 复杂组件能力（表格拖拽排序、树表联动）与 TDesign 相当但 API 繁琐度更高；
- 主题定制能力弱于 TDesign 的 Token 体系。

### Ant Design Vue / Antd

**优点**

- Antd（React 版）是中后台事实标准，ProComponents 封装度最高；
- 设计语言成熟。

**缺点**

- Antd 对应 React 技术栈，与框架结论冲突；
- Ant Design Vue 为社区移植，**更新节奏滞后于 React 版**，与新特性/修复存在时间差；
- 同样存在与原型视觉体系不一致的还原成本。

### 结论

**维持 TDesign Vue Next**。决定性因素是原型同构带来的还原效率与视觉一致性；组件能力对本项目无短板；其社区短板用"项目内自封装业务组件层"对冲，反而利于长期维护。

## 5. 配套技术选型

### 5.1 构建与语言：Vite + TypeScript

- 已确认仅支持现代浏览器，无需 `@vitejs/plugin-legacy`，构建目标 `es2020+`，产物体积与构建速度最优；
- TypeScript 全量开启严格模式，接口层按后端契约生成/手写 DTO 类型，保证 45+ 页面长周期维护的重构安全。

### 5.2 状态管理：Pinia

- 按业务域拆分 store：`identity`（用户/角色）、`model`（供应商/模型）、`cost`（预算/账单）、`security`（策略/规则）、`system` 等，与菜单模块一一对应；
- 跨页共享数据（部门树、字典枚举、当前用户权限）集中缓存，避免各页重复请求。

### 5.3 路由与权限：Vue Router + 动态权限路由

- 原型已验证存在完整路由守卫（登录态校验 + redirect 回跳），落地时实现：
  - 登录后按角色拉取菜单/权限，动态 `addRoute` 注册；
  - 按钮级权限指令 `v-permission`（如"禁用 Key""批量审核"等操作）；
  - P1 功能以**菜单配置 + 路由占位**方式预留，配置开关打开即生效，不改代码。

### 5.4 图表：ECharts

- 覆盖仪表盘 KPI 趋势、成本消费趋势、部门 Top10、审计报表、使用分析；
- `echarts/core` 按需注册，控制包体积；封装统一 `<ChartCard>` 组件承载标题、时间范围、空态（原型已出现"所选范围暂无消费数据"空态）。

### 5.5 HTTP 与 Mock

- Axios 单实例封装：统一鉴权头、错误码处理、脱敏字段约定、文件下载（审计导出）；
- 后端 REST API 并行开发：接口契约先行（路径/入参/出参文档化），前端以 **vite-plugin-mock（开发期）+ MSW（组件/测试期）** 双轨 Mock，联调阶段零改动切换真实地址（环境变量切换 baseURL）；
- 与后端约定统一响应壳 `{ code, data, message }` 与分页结构，Axios 拦截器统一拆壳。

### 5.6 工程化

- ESLint（`@vue/eslint-config-typescript`）+ Prettier + Stylelint；
- husky + lint-staged 提交卡口；commitlint 约定式提交；
- 环境分层：`.env.development`（Mock）/ `.env.staging`（联调）/ `.env.production`。

### 5.7 目录与架构（按业务域模块化，支撑 P1 扩展）

```
src/
├── api/            # 按域划分，与后端契约一一对应
├── assets/
├── components/     # 通用封装：FilterBar、ProTable、ChartCard、DetailDrawer
├── composables/
├── layouts/
├── router/         # 静态路由 + 动态权限注册 + P1 占位
├── stores/         # Pinia，按域拆分
├── styles/
├── utils/
└── views/
    ├── dashboard/
    ├── identity/   # users / groups / roles / keys
    ├── model/      # providers / models / logical
    ├── cost/       # overview / bills / budgets / approvals
    ├── security/   # access-control / content-rules / detection / audit
    ├── audit/      # records / sessions / events / reports
    ├── system/     # settings / plugins / cluster / license / ...
    ├── personal/
    └── routing/    # P1 占位，开关控制
```

## 6. 风险与应对

| 风险                                 | 应对                                                  |
| ------------------------------------ | ----------------------------------------------------- |
| TDesign 社区较小，冷门问题检索成本高 | 自封装业务组件层收敛用法；问题优先查官方 Issue/源码   |
| 审计记录等大表格性能                 | TDesign Table 虚拟滚动 + 后端分页；导出走后端异步任务 |
| 接口并行开发进度错位                 | 契约先行 + 双轨 Mock；联调清单按模块倒排              |
| 权限模型后期变更                     | 菜单/按钮权限全部配置化驱动，不写死前端               |
| P1 功能接入扰动既有代码              | 业务域目录隔离 + 路由/菜单开关占位，接入时零改动      |

## 7. 最终结论

**Vue 3 + TypeScript + Vite + TDesign Vue Next + Pinia + Vue Router + ECharts + Axios**。该组合在团队熟练度、原型还原成本、业务复杂度匹配度、P1 扩展弹性四个维度均为最优解，可直接进入开发阶段。
