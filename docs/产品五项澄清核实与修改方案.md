第1、2、3项仍有后端差异，第4项为入口之间部分不一致；第5项后端已经支持不调用 C05 直接提交，需调整前端流程及对接说明。价格、计费、检测和上架均以系统现有能力为基准。

## 第一项 用户组管理与成员范围

### 现有行为与证据

“拥有权限”必须区分 READ 与 WRITE。当前组接口使用 `identity.groups`：READ 用于查看，WRITE 用于创建、编辑、删除和成员变更。不能把只读权限直接解释为可删除。

1. **普通角色不能查看所有组。** [组查询](../../backend/internal/repository/aggregate/groups/query.go) 第18至20行只允许根范围、空组或包含本部门子树成员的组。纯外部门组被隐藏；混合组虽可见，但不能管理。
2. **普通角色不能编辑、删除所有组。** [组投影](../../backend/internal/logic/groups/query.go) 第21至37行在存在外部门成员时返回 `can_manage=false`、`write_blocking_code=OUT_OF_SCOPE`。[组写授权](../../backend/internal/logic/authorization/group.go) 第46至73行把全部既有成员和本次目标合并，再进入[统一写授权](../../backend/internal/logic/authorization/write.go) 第130至149行检查成员部门。仅修改描述，也会被旧成员范围阻止。
3. **跨部门移除不符合。** 移除也走上述全部成员范围校验，因此普通有组写权限者无法移除外部门成员。[成员接口契约](../../backend/api/groups/v1/members.go) 第63至71行还明确描述了这一旧规则。
4. **新增范围存在反向放大。** [组范围策略](../../backend/internal/model/authorization/group_scope.go) 第5至22行只给精确内置 `DEPARTMENT_ADMIN` 全局特例，且操作清单包含添加成员。同权限的自定义角色或复制角色没有特例；内置部门管理员却能添加外部门人员。
5. **候选与成员查看共用范围。** [成员候选业务](../../backend/internal/logic/groups/members_query.go) 第72至98行会拒绝混合组；[成员查询](../../backend/internal/repository/aggregate/groups/members.go) 第17至20行使用同一个 `Global` 决定是否去除部门限制。[部门选项](../../backend/internal/repository/aggregate/groups/departments.go) 第23至25、42至54、77至78行也沿用此范围，因此不能表达“成员可全局移除、添加候选仅本部门子树”。
6. **已有重放仍携带旧限制。** [组命令重放](../../backend/internal/logic/groups/replay.go) 第29至47行检查历史全部成员的部门，不能只改首次执行路径。

现有测试也明确保护旧规则：[组 HTTP 测试](../../backend/tests/integration/groups_http_test.go) 第296至321行断言混合组不能管理、外部门组404；[组成员测试](../../backend/tests/integration/groups_members_test.go) 第330至335行断言混合组候选、添加和移除403；[部门管理员测试](../../backend/tests/integration/department_admin_test.go) 第252至258行验证复制角色不享有全局范围，第273至274行允许内置部门管理员重新添加外部门成员。这些断言需按新产品规则调整，而非原样沿用。

### 建议目标行为

| 行为                                                   | 对象范围                                       | 权限要求                                      |
| ------------------------------------------------------ | ---------------------------------------------- | --------------------------------------------- |
| 列表、详情、组翻译、现有成员查看                       | 所有用户组；成员仅提供组管理所需的现有安全字段 | identity.groups READ                          |
| 编辑、删除、组翻译修改                                 | 所有用户组，不因既有外部门成员拒绝             | identity.groups WRITE                         |
| 移除成员                                               | 所有组的现有成员，可跨部门                     | identity.groups WRITE                         |
| 创建时选择初始成员、添加成员、添加候选及其部门树和搜索 | 操作者真实部门及以下部门                       | identity.groups WRITE；候选按既有读取权限契约 |

普通角色、内置部门管理员和复制角色采用相同规则。根部门操作者的部门子树天然覆盖全树。建议不再保留“某内置角色可跨部门添加”的特例。

### 详细修改方案

1. 把组对象范围、现有成员查看/移除范围、新增成员范围拆开表达。取消以 `DepartmentAdmin` 决定组域全局范围的业务特例；按接口的 READ/WRITE 授权后，组对象均为全局。操作者真实部门、通用用户管理范围、通用部门管理范围保持原事实。
2. `LockGroupAuthorized` 仍完整展开并锁定受影响成员，保留统一锁序和事务。编辑、翻译、删除、移除不再对外部门既有成员执行部门范围拒绝；创建和添加仅对本次申请添加的目标执行当前部门闭包检查。重复添加、目标不存在和成员关系状态沿既有语义处理，不能让“已是成员”绕过本次目标范围检查。
3. 混合组允许添加本部门子树成员。批次中一人越界时整批拒绝，不先过滤再部分成功；创建初始成员采用同样规则。
4. 现有成员查询可返回外部门成员的最小管理投影，以便选择移除；添加候选、创建前候选、添加用部门逐级加载和部门名称搜索均固定为当前部门子树。现有 `/groups/member-department-options` 同时用于成员筛选，应拆分用途：新增候选使用本部门子树；现有成员筛选仅返回绑定 `group_id` 的真实组内部门最小选项，或另设这一专用入口，允许筛选外部门既有成员。不能通过组权限获得全公司的通用用户或部门候选目录。
5. 调整 `can_manage`，以写权限和对象可操作性表示可编辑、删除、移除，不再由外部门成员阻断；完整组成员数可返回。`has_out_of_scope_members` 如保留，表示“存在新增范围外的既有成员”，不再表示禁止管理。[权限视图](../../backend/internal/logic/authorization/views.go) 第40至44行需把组对象范围改为 GLOBAL，并在契约中单独说明成员添加范围；前端不得将 GLOBAL 解释为可全局添加。
6. 重放按操作类型重验当前权限及目标合法性：移除/删除不因历史外部门成员失败；添加仍重验所申请目标的当前部门。保留幂等结果、成员版本/游标失效、审计、Outbox 和删除组时清理模型授权的事务机制。
7. 不更改默认角色权限分配，不批量重写既有组或成员数据。当前审计查询有自己的权限和历史范围，此次组对象全局化不自动扩大历史审计访问。

## 第二项 模型详情授权管理可选择所有用户组

### 已明确的页面与权限边界

适用位置为截图红框：“模型管理详情 → 授权管理 → 用户组授权”的搜索多选下拉。可选集合覆盖全部真实存在的用户组，包括空组、纯外部门组、混合组，不根据组内成员的部门限制候选。

本条沿用现有授权权限：A12/A01 为 `model.permissions READ`，A02 为 `model.permissions WRITE`。页面本身按现有模型查看权限打开；选择器和授权接口不额外要求 `identity.groups`。不把 `model.models` 与 `model.permissions` 合并，也不据此增加默认角色权限。第1项的组管理范围调整仍独立按 `identity.groups` 执行。

“所有用户组”指候选范围完整，继续使用后端分页和搜索：默认每页20条，上限100条，名称搜索和稳定排序沿现有约定，不要求单次返回全量。已授权组仍属于全量候选，前端依据 A01 标识为“已授权”并避免重复勾选；名称相同的组以 UUID 区分。

### 当前差异与必要调用链

1. [A12 候选 SQL](../../backend/internal/repository/aggregate/modelauthorization/subject_candidates.go) 第126至132行排除含任何范围外成员的组。[前端指南](../model-access/rebuild-v14/07-前端协同对接指南.md) 第704行将此选择器用于模型详情，第1260行也记录它共享于其他授权场景。
2. [A01 已授权查询](../../backend/internal/repository/aggregate/modelauthorization/query.go) 第87至94行同样过滤混合组；若仅放开下拉，保存后会看不到该授权。
3. [A02 保存与重放](../../backend/internal/logic/modelauthorization/write.go) 第89至103、126至132、151至153行调用统一主体检查；[ScopedSubject](../../backend/internal/repository/aggregate/modelauthorization/subject.go) 第38至54行会因组含外部门成员返回 NOT_FOUND。
4. [授权写入后回读](../../backend/internal/repository/aggregate/modelauthorization/model_delta.go) 第89至101行还调用 DirectGrants 组装 Added；此处若仍按旧范围过滤，会因返回新增数量不足而回滚。全局组策略须贯穿该回读。

### 接口与前端流程

1. 首次打开授权管理按原约定调用 A01，取得当前模型的直接授权及 `grant_version`。组关系按全局组范围回显；部门、用户关系保持各自原范围，不展开组成员。
2. 红框下拉使用 A12，显式传入限定用途 `use_case=MODEL_DETAIL`：

   ```http
   GET /api/v1/model-access/model-permission-subjects?subject_type=USER_GROUP&use_case=MODEL_DETAIL&page=1&page_size=20
   ```

   搜索加 `q`，翻页保留相同用途和搜索条件。响应形状保持现有 SubjectViewPage，`total` 为全局组范围内符合搜索条件的总数，`manageable` 仍由现有授权写权限决定，只返回组 ID、名称等最小投影。

3. 新增 A12 可选枚举字段 `use_case`：唯一非空合法值为 MODEL_DETAIL，且仅允许与 USER_GROUP 搭配；未知值、空值、重复值及与其他主体类型组合按正式查询校验约定拒绝。省略时保留原候选范围。USER_GROUP 仍拒绝 `department_id/parent_id`，不接受客户端传任意部门根或全局布尔开关。
4. 该用途字段用于区分共享选择器的业务场景，权限仍由服务端实际会话校验。选择用途不产生新权限；模型详情只通过 A02 保存，不把该字段用于组成员管理。
5. 点击添加或撤销使用现有 A02，携带 `expected_grant_version` 及增删差异。组新增、撤销均按全局组对象判断；无须改变 A02 请求结构。保存成功按响应更新版本，再刷新 A01；版本冲突重新读取并让用户核对本地选择。
6. 组在选择后被删除时，保存按不存在对象拒绝；批次整笔回滚。组成员后来跨部门变化，不使模型详情的组授权消失。重复添加继续按既有增量与幂等语义处理，不能新增重复关系。

### 后端分层实现与影响控制

1. 在内部模型定义明确的组主体策略，例如 `GroupSubjectScope=DEPARTMENT_SUBTREE/GLOBAL`。策略由服务层按已注册操作和校验后的用途推导，不能由客户端直接提供。原真实部门根不变，USER/DEPARTMENT 的范围逻辑不变。
2. A12 仅在 USER_GROUP 且 MODEL_DETAIL 时选择全局组 SQL；页内查询和总数共用相同条件。默认候选、部门树、人员筛选继续原实现。
3. A01 和 A02 的模型侧上下文使用全局组策略：贯穿 A01 分页/不分页查询，A02 预读当前关系、实际差异计算、主体存在性校验、ApplyChanges 的写后回读及幂等重放。撤销仍按授权关系 ID，并校验其确属当前模型。
4. 共享 Repository 显式接收策略，或提供有明确名称的专用查询/校验方法；不得直接把共用 ScopedSubject 和 DirectGrants 的所有 USER_GROUP 分支无条件改为全局。模型详情的写后回读必须与本次写入采用同一策略。
5. A03 批量、M03 初始授权、M05 授权修改及 A09/A10/A13 主体侧入口继续原有范围策略；不传 MODEL_DETAIL 的其他 A12 消费方继续原范围，避免“候选放开、对应保存仍拒绝”。第4项对待审核状态的调整独立应用于原定主体侧入口。
6. 保留权限、CSRF、授权版本、完整锁序、事务、审计、Outbox 和组删除清理；组全局可选不扩展通用用户/部门目录或历史审计范围。A 域修改先落到 [DTO 模板](../../scripts/templates/v14-authorization.go.tmpl)，再统一生成。
7. 原稿发现的混合组继承来源/数量查询与数据面口径差异列为独立观察项，不因本次下拉需求自动扩大改造范围。本批不改 A04/A11 或用户详情计数；如另行修复，应单独说明口径和验收。

新增用途字段是为复用现有 A12 且保留其他消费者语义。此次不新建第二套组列表接口，也不要求前端借用通用 `/groups` 及其身份权限。

## 第三项 供应商编辑固定模板

### 现有行为与证据

P05 为 `PUT /api/v1/model-access/providers/{provider_id}`。[供应商接口](../../backend/api/modelaccessv14/v1/provider.go) 第276至279行明确允许改选模板，`ProviderUpdate` 第363至374行要求提交 `template_key`、`template_version_id` 并允许与原绑定不同。

[控制器](../../backend/internal/controller/modelprovider/write.go) 第40至57、116至127行把模板字段传入保存逻辑并要求编辑也提供模板。[业务保存](../../backend/internal/logic/modelprovider/write.go) 第105至126行在版本不同后选择当前模板，第153至181行锁定实例后使用选中模板；[实际 UPDATE](../../backend/internal/repository/aggregate/modelprovider/write.go) 第79至98行修改模板 key、版本 ID 和 revision。已有模型关联不会阻止此入口改绑。

这并非仅前端展示问题。[接口字典](../model-access/rebuild-v14/04B-API接口与字段字典.md) 第265至284行、[前端指南](../model-access/rebuild-v14/07-前端协同对接指南.md) 第134、1295、1499行也明确支持编辑改选模板。

### 详细修改方案

1. 产品已确认：供应商创建后同时固定模板 key 与模板版本。**同 key 换到新版本也属于改绑，普通编辑不允许。** 目录发布不自动升级既有实例，本次不新增模板升级或迁移入口。
2. **推荐收紧 P05 请求契约，移除更新 DTO 中两个模板字段，创建 DTO 保留。** 服务端按供应商已绑定模板解释编辑参数；编辑页只读显示原模板及版本，取固定模板定义渲染。按现有 strict-json 规则拒绝旧模板输入字段。P05 的 `minBodyProperties` 从7改为5，更新只要求 `expected_version/name/base_url/security_level/public_config`；创建仍为6项并保留模板校验。当前 `Writer.Save` 在事务前执行的 [Normalize](../../backend/internal/model/modelprovider/write.go) 第46至53行无条件要求模板 key 和版本 UUID，必须拆分创建/编辑的必填检查和规范化：编辑事务前只规范化公共输入，锁实例后读取固定模板并注入内部保存计划。只删 DTO 字段会导致正常编辑全部被拒绝。
3. 编辑逻辑移除 `SelectCurrentTemplate` 及改绑分支，只读取锁定实例的固定模板。供应商目录发布新版本后，旧实例仍按固定版本编辑；创建仍只采用当前可用模板。
4. Repository 的普通 UPDATE 去除 `template_key`、`template_version_id`、`template_revision` 赋值。新增 INSERT 仍写入绑定。既有供应商不自动迁回旧版本，不需要数据库结构迁移。
5. [保存计划](../../backend/internal/logic/modelprovider/write.go) 第256至310行的 `rebound` 秘密重建分支及[余额配置](../../backend/internal/logic/modelprovider/balance.go) 的模板比较路径需同步清理，保留固定模板内的调用秘密/余额秘密省略语义、加密、实际连接变更与版本推进。只改名称不应推进连接代次；改连接参数或秘密按现有规则推进。
6. 保留权限、CSRF、幂等、`expected_version`、事务内重验和审计。失败不能写入供应商配置、密文、版本、余额状态或成功回执。
7. 编辑请求不再接受模板字段；前端创建页继续提交模板选择，编辑页仅展示。同步修改 P05 描述、ProviderUpdate、生成客户端和表单，移除旧的改绑引导，不保留两套编辑输入语义。

## 第四项 待审核模型可提前配置授权

此条按模型生命周期 `PENDING_REVIEW` 理解，含待审核模型对用户、部门、用户组三种主体的直接授权；不改变模型审核流程。

### 现有行为与证据

| 入口                                           | 当前状态限制                             | 待审核模型现状                                      |
| ---------------------------------------------- | ---------------------------------------- | --------------------------------------------------- |
| M03 创建初始授权                               | 创建 DRAFT 并写入关系                    | 已有提前配置授权能力                                |
| A02 单模型增删授权                             | 锁模型核实存在和授权版本，无 ACTIVE 判断 | 从代码看允许 PENDING_REVIEW，仍受主体范围及权限约束 |
| A03 跨模型批量添加                             | 同样无 ACTIVE 判断                       | 从代码看允许 PENDING_REVIEW，仍受主体范围及权限约束 |
| A06/A08/A10 用户、部门、用户组直接授权集合替换 | 只有本次新增模型要求 ACTIVE              | 新增待审核模型返回422 VALIDATION_FAILED             |
| A14 用户批量增量添加                           | 只有真正新增要求 ACTIVE                  | 新增待审核模型返回422 VALIDATION_FAILED             |
| A13 主体侧可选模型                             | SQL 只取 ACTIVE                          | 待审核模型不会出现在候选                            |
| 已有关系展示、保留、撤销                       | 允许非 ACTIVE 关系                       | 此部分无需因新澄清删除关系                          |

证据：[A02](../../backend/internal/logic/modelauthorization/write.go) 第66至118行、[A03](../../backend/internal/logic/modelauthorization/batch.go) 第89至128行与[模型锁及关系写入](../../backend/internal/repository/aggregate/modelauthorization/model_delta.go) 第15至80行未检查 ACTIVE；[主体集合保存](../../backend/internal/logic/modelauthorization/subject_write.go) 第126至129行、[用户增量添加](../../backend/internal/logic/modelauthorization/user_delta.go) 第171至179行明确拒绝非 ACTIVE；[候选 SQL](../../backend/internal/repository/aggregate/modelauthorization/model_candidates.go) 第22至27行只取 ACTIVE。错误映射见[授权控制器](../../backend/internal/controller/modelauthorization/write.go) 第108至109行。

### 详细修改方案

1. 将主体侧“本次新增可授权状态”从 `ACTIVE` 扩展为 `ACTIVE + PENDING_REVIEW`，抽取业务状态判断供 A06/A08/A10/A14 复用；A13 候选同步扩展，不能只放开提交或只放开显示。
2. 保留 M03 草稿初始授权、A02/A03 现有能力。本条不额外改变 DRAFT、TESTING、SUSPENDED、RETIRED 在各入口的既有新增语义；如需所有状态彻底统一，另作产品决定。
3. 继续以实际新增、保留、撤销差异判断，不把候选列表当作完整授权集合。已有非 ACTIVE 关系仍能展示、保留或撤销；批次存在不允许新增的模型时整批回滚。调整 `ErrGrantModelInactive` 命名/文案，避免已放行待审核后仍宣称“新增必须 ACTIVE”。
4. **保存授权关系不等于可调用。** [数据面解析](../../backend/internal/repository/aggregate/modeldataplane/resolve.go) 第30至34行仍仅允许 ACTIVE；[生命周期](../../backend/internal/model/modelcreation/lifecycle.go) 第51至54行审核通过才转 ACTIVE、拒绝回 DRAFT。待审核时显示已有授权但不可用；审批后，在用户、Key、条款、供应商、模板及调用配置等既有条件均满足时可调用。审核拒绝不自动删授权，重审通过后按现有事实生效。[授权可用性](../../backend/internal/repository/aggregate/modelauthorization/access_sources.go) 第113至116行继续报告 MODEL_NOT_ACTIVE。
5. 更新 A 域模板、生成契约、候选状态说明、主体侧前端选择与提示。授权版本、幂等重放、审计和关系去重沿现有机制；回放成功历史命令不因后来模型转状态重复执行新增。
